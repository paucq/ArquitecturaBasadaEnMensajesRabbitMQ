# CP-09 — Resilient — RabbitMQ

- ID del caso: CP-09; corrida 03, 2026-10-27; `ORD-b7a74952-2957-49cb-a5db-f88d7b2ce443`.
- Arquitectura: RabbitMQ; orders-api → cola `pedidos` → notification-worker (dos instancias locales).
- Objetivo: comprobar que la indisponibilidad simulada del consumidor no impide aceptar/publicar pedidos en la API y que el pedido pendiente se procesa cuando regresa el consumidor. Guía p. 4: «El sistema soporta caída del consumidor»; no exige kill ni interrupción durante procesamiento para CP-09.
- Precondiciones: API/broker running y healthy, workers inicialmente running ([Compose inicial](../consumidores-apagados/corrida-03/01-antes-stdout.txt)). Tras detenerlos, [baseline](../consumidores-apagados/corrida-03/baseline.json) durable=true, Consumers=0, Ready/Unacked/Total=0/0/0. Dos workers detenidos y un pedido son parámetros seleccionados de este ensayo, no mínimos impuestos por el profesor.
- Datos de entrada: un POST /orders, application/json, `{"customerName":"Pedro","product":"Libro de arquitectura","quantity":1}`; [request/respuesta originales](../consumidores-apagados/corrida-03/06-postman-stdout.txt).
- Pasos ejecutados:
  1. Se comprobó el estado inicial y se simuló caída mediante [stop controlado](../consumidores-apagados/corrida-03/03-stop-comando.txt): `docker compose -p qa-taller-integracion-rabbitmq stop notification-worker`, de 01:39:19.324175 a 01:39:30.165185 UTC, [exitcode del comando 0](../consumidores-apagados/corrida-03/03-stop-exitcode.txt). [Compose tras stop](../consumidores-apagados/corrida-03/04-parados-stdout.txt): ambos exited, ExitCode de contenedor 137; API/broker healthy. No se confunde ese 137 con el éxito del comando ni se afirma parada graciosa.
  2. Tras espera acotada de Consumers=0 y baseline vacío, se publicó una única solicitud con [Postman CLI](../consumidores-apagados/corrida-03/06-postman-comando.txt), [exitcode 0](../consumidores-apagados/corrida-03/06-postman-exitcode.txt). No hubo otra publicación para documentar este caso.
  3. Se verificó [order_published del mismo ID](../consumidores-apagados/corrida-03/logs-mismo-id.txt), [cola pendiente](../consumidores-apagados/corrida-03/cola-final.json) y [Compose durante la demostración](../consumidores-apagados/corrida-03/10-final-stdout.txt). El [snapshot histórico](../consumidores-apagados/corrida-03/resultado.json), a 01:39:45.394411+00:00, conserva ambos workers exited y Consumers=0. No describe el estado actual.
  4. Después de la captura pendiente, se verificaron precondiciones y se ejecutó una sola vez [start notification-worker](../consumidores-apagados/corrida-03/consumo-posterior/03-start-comando.txt), [exitcode 0](../consumidores-apagados/corrida-03/consumo-posterior/03-start-exitcode.txt), sin nueva publicación. Se esperó como máximo 45 s y se registraron [logs del mismo pedido](../consumidores-apagados/corrida-03/consumo-posterior/logs-mismo-id-notification-worker.txt) y [resultado final](../consumidores-apagados/corrida-03/consumo-posterior/resultado-final.json).
- Resultado esperado: ante consumidor no disponible, la API sigue aceptando/publicando; el broker retiene el pedido pendiente, que se procesa al regresar el consumidor. No se requiere procesamiento inmediato mientras está detenido.
- Resultado obtenido: HTTP 202 Accepted en 27 ms, una request, 4/4 aserciones, exitcode 0. API/broker healthy antes y durante la demostración; publicación **2026-10-27T01:39:39.627Z** con ambos workers detenidos. Cola durable: Ready=1, Unacked=0, Total=1, Consumers=0; captura Persistent=1. Resultado final a **2026-10-27T01:46:40.985636+00:00**: ambos workers running, API/broker healthy, Consumers=2, Ready/Unacked/Total=0/0/0. Horas UTC de aplicación, no prefijos Docker ni hora local de UI; 27 ms es observación, no SLA.

- Estado: Cumple. Conclusión propia sobre el ensayo documentado, no calificación del profesor.
- Análisis técnico: la caída simulada por stop elimina los consumidores disponibles, pero no bloquea la aceptación/publicación observada. La cola amortigua la indisponibilidad hasta el regreso del worker. Management no muestra ID ni payload: la correlación experimental procede del baseline vacío, publicación única y logs API/worker coincidentes, no de Get messages ni de inspección de payload. [CP-11](../consumidores-apagados/corrida-03/reporteCP11.md) usa este experimento para almacenamiento y separación temporal; CP-09 enfatiza continuidad de API ante indisponibilidad y regreso del consumidor. [CP-07](../responsive/reporteCP07.md) analiza respuesta sin esperar consumo. Este experimento no cubre CP-12: aquí no se interrumpió b7a en Unacked antes del ack ni se observó reentrega (redelivered=false); no demuestra recuperación de trabajo en vuelo. La recuperación se verificó después, en una corrida independiente, y quedó cerrada en el [reporte CP-12](../recuperacion/reporteCP12.md). Se conservó y procesó este ID, sin generalizar «no pérdida», exactly-once, alta disponibilidad, downtime cero, caída del broker, fallo AMQP o capacidad bajo carga. Los intentos 01/02 y sus fallos de observación/instrumentación permanecen en el [historial](../consumidores-apagados/RESUMEN.md), no se mezclan con esta corrida ni con la traza 8d de CP-06. Cierre exclusivamente documental, sin operaciones runtime ni cambios de aplicación.
