# CP-06 — Trazabilidad del flujo — RabbitMQ

- ID del caso: CP-06; corrida de trazabilidad 01, 2026-10-27 (UTC).
- Arquitectura: RabbitMQ; orders-api → broker RabbitMQ / cola pedidos → notification-worker, con dos instancias activas.
- Objetivo: Seguir el mismo orderId / correlationId en los registros de API, broker y consumidor, como exige la guía p. 4.
- Precondiciones: API y broker healthy, dos workers running, Consumers=2, cola vacía y durable=true. RabbitMQ 4.4.0; plugin de diagnóstico inicialmente deshabilitado y Firehose apagado. [Estado inicial](../trazabilidad/corrida-01/initial-state.json). Activación temporal autorizada para esta prueba local; sin cambios de aplicación o Compose.
- Datos de entrada: Un POST /orders con JSON `{"customerName":"Pedro","product":"Libro de arquitectura","quantity":1}`. Pedido `ORD-8d488fb8-62c9-4e37-935d-31aed2a8aa9e`; correlationId igual al orderId. Es una corrida distinta de la usada para CP-01/02/03/11.
- Pasos ejecutados:
  1. Se conservaron versiones, salud, plugins, vhost, estado de cola y consumidores.
  2. Se habilitó temporalmente el plugin nativo `rabbitmq_tracing` online y se creó una traza propia con formato JSON, patrón `#` y vhost `/`; se comprobó que su consumidor estaba listo antes de publicar.
  3. Se ejecutó una sola solicitud Postman CLI: HTTP 202, 1655 ms, 4/4 aserciones y exitcode 0. [Comando y metadatos](../trazabilidad/corrida-01/017-postman-single-request-execution.json); [stdout original](../trazabilidad/corrida-01/017-postman-single-request-stdout.txt).
  4. Se exportó el archivo nativo del broker y se conservaron logs API/worker del mismo ID; se verificaron `message_id`, `correlation_id` y `orderId` del payload decodificado.
  5. Se eliminó solo la traza propia y se apagó Firehose. Tras interrumpirse el subagente, el padre verificó independientemente que el plugin ya estaba deshabilitado y que el estado inicial estaba restaurado, sin volver a publicar ni reiniciar servicios.

- Análisis técnico: El registro del broker procede de su plugin nativo de diagnóstico, no de una línea inventada de la aplicación ni de contadores de Management. Sus logs operativos habituales no registraron este ID: [filtro vacío conservado](../trazabilidad/corrida-01/logs-rabbitmq-same-id.txt). En el formato nativo `received` representa entrega desde el broker, no ack ni procesamiento completo; esto último se acredita por el evento del worker. El log API puede aparecer después del evento del broker porque se escribe tras confirmar la publicación. La traza tiene coste de recursos y registra payload; no sirve para extrapolar rendimiento, exactly-once o recuperación ante caídas. La interrupción dejó sin metadatos finales al orquestador: no se inventa exitcode para la deshabilitación del plugin; se acredita la restauración mediante inspección independiente. Tres tests offline del formato pasaron; enlaces, IDs, etapas y limpieza se verificaron. Conclusión propia, no calificación del profesor.
